## 2. The fix — why THIS form

**Two windows, selected by the phase.** Not one longer window.

```
app/webview/sotto_webview.py:423   WORKER_SILENCE_MS = 30000        (unchanged, the post-load contract)
app/webview/sotto_webview.py:444   WORKER_LOAD_SILENCE_MS = 180000   (new, the pre-load ceiling)
```

`WorkerBridge._silence_window()` (:8041) returns:

* **before `model-loaded`** — `max(1.0, (load_silence_ms - elapsed_ms) / 1000)`: the load ceiling,
  measured from the spawn and **shrinking** as the load runs.
* **after `model-loaded`** — `silence_ms / 1000`: the old 30 s contract, untouched.

`_on_silence()` (:8139) branches on `self.loaded`:

* **inside the ceiling** → `BRIDGE_SILENT_LOADING ms=… pid=… window_ms=… because=model-not-loaded`,
  re-arm, **return**. Nothing is killed and nothing is painted: the panel is already showing
  `model-loading`, which is the truth.
* **past the ceiling** → `BRIDGE_SILENT_LOAD_TIMEOUT … because=model-never-loaded`, the panel is
  told *"Worker is still loading the model"* / *"Model load timeout"*, and the child is restarted with
  `reason=load-timeout`.

### Why not one longer window

A single 180 s window would let a worker that wedges **after** loading hold its caption channel for three
minutes — the exact failure the watchdog exists to catch, with the owner staring at a dead caption
channel and no diagnosis. A single 30 s window is the defect. **The phase is the only signal that
distinguishes the two**: the worker is obliged to be silent while it loads and obliged to be talkative
once it has.

### Why 180 s

The owner's own bound, verbatim — *"faz o model sair de load apos 3 minutos"*
(`docs/audit/load-churn.md:9`). Not a number I derived. Note this is a **different mechanism** from the
`WORKER_RELOAD_MIN_INTERVAL_MS = 180000` already at `:480` (a minimum interval between applied reloads,
`load-churn.md:181-184`); the two share the number because both are the owner's own bound, and they are
not interchangeable.

### Why the ceiling is still enforced

Otherwise the cure trades a spurious kill for a worker that can wedge forever with the panel sitting on
`model-loading` for the rest of the session. A load that never finishes **is** restarted, loudly, and the
panel says why.

### Why `BRIDGE_LOAD_MS`

The shell's own measurement of the load — spawn to `model-loaded` — logged **next to the worker's own**
`load_s` on the same line. One boot log therefore carries both, and the two can be compared instead of
assumed equal. That comparison is what makes the startup stutter attributable to a phase (deliverable 3).

## 3. The second deliverable — the hour on every line

`_stamp()` (:621) + a rewritten `log()` (:645) now prepend the hour:

```
2026-10-12 14:03:04.743 sotto: ARM_S1_PROBE
```

**Leading, not trailing, for two reasons:**

1. A log line reads time-first, which is what makes the file comparable with every other clock on this
   box (`Get-Process .StartTime`, the Task Scheduler history, the Event Log). The measurement this front
   needs is the distance between a shell line and a worker line taken tens of seconds apart.
2. **The `sotto: ` tag keeps its exact position and spelling.** Measured repo-wide: every consumer
   reads these lines by substring or by `split('sotto: ', 1)[-1]` (12 such sites in 11 files), and
   **`startswith`/`find`/`indexOf` on the tag = 0 matches repo-wide** — nobody anchors a regex on it.
   So the tag keeps matching while the hour is added in front of it.

The stamp is produced by `_stamp()` inside `log()` — the ONE function both the stdout print and the
`--log` mirror write through — so `warn()` and every other caller inherit it without a second code
path. Proved in-process, twice: `_main/s7-silence-window-oracle.py` arm S1 (stdout) and
`_main/s7-boot-cost.py` arm `log` (the `_open_log()` + `log()` + read-back file path).

## 6. Deliverable 3 — the startup stutter: what is and is not attributed

**Attributed, with numbers:**

* The defect made every cold boot that hit it load the model **twice** — kill at 30 s, respawn, load
  again. One load's disk half is ≥ 1.04 s, so the double is ≥ 2.1 s of reads plus two CUDA contexts in
  the first minute after logon. **42** such kills are in the log.
* The eager panel set is 627 543 B on the first frame's critical path; **1 287 846 B** more used to be.

**Not attributed, and why:**

* **The cold load's exact duration.** Only a **> 30 s lower bound** exists (line 99631: the watchdog
  fired at 30 s and the worker had not finished). There is no upper bound.
* **The stutter's phase breakdown.** The pre-patch log has **0** stamped lines — every line in it was
  written before this front. The new timestamps cannot retroactively date them.
* **The VRAM copy / CUDA session creation cost.** Not measurable without a second copy of a 2 GB model
  in VRAM. That is front S8's, not mine.
* **The WebView2 boot phases** (`STAGING_SEEN` → `STAGING_LOADED` → `RECEIVER_READY` →
  `PANEL_LAZY_GATE_ARMED`). Their order is in the log; their duration is not.
* **Whether `lazy-assets.js` changes the first paint.** It is gated by the existing lazy-asset gates; I
  ran no browser and measured no frame.

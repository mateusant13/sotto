# The INT8 route, and what was actually eating the words

**Date:** 2026-10-06 · **Repo:** `H:/sotto` · **Lane:** `SottoInt8Route`
**Predecessor:** `docs/accuracy-int4-vs-fp16-20261006.md`

**Answer in one line:** the 4-bit weights were innocent. The greedy walk in
`worker/sotto_worker.py` was the defect, in two separate places; with the walk
corrected, the INT4 export is fluent, and an INT8 export of the *same*
generation is fluent and recovers ~17 % more tokens. `config.json` now selects
the INT8 export, the INT4 export stays one flag away, and no runtime was
swapped — `onnxruntime` + `onnxruntime-genai` still drive everything.

## 2. The two defects, each isolated by a single changed line

### Defect A — the label cursor indexed the wrong array

```
dd = np.transpose(dout, (0, 2, 1))[:, k0:, :]      # k0 counts EMITTED SYMBOLS
ti += hit[0];  k0 += hit[1] + 1
dout, h, c = self._decode(np.array([[blank, hit[2]]]), h, c)
```

`decoder_output` holds 1–2 positions. `k0` grows by one per emitted symbol, so
after two emissions the slice is empty and the chunk ends early. The walk also
scanned every remaining frame for any non-blank at once, which lets it step over
frames whose prediction it never evaluated.

The canonical RNN-T greedy search needs **no cursor at all**: the LSTM emits
position *i* after consuming `targets[:i+1]`, so with `targets = [the one symbol
just emitted]` and carried `h`/`c`, position 0 **is** the new prediction vector.

### Defect B — the decoder state was carried across the chunk boundary

The acoustic history already crosses the boundary in the *encoder* cache
(`cache_last_channel` / `cache_last_time`). Carrying the prediction network
across the boundary as well duplicates word tails.

Isolated arm (same file, same weights, CPU, only the carry convention differing):

```
carry across chunks -> 86 tokens (int4) / 108 (int8)
    "Goinging along country roadskingss infty schoolros dayy for for a
     fortnight.  he'll have to inance at somece of worshi on morningning,"
re-prime per chunk  -> 81 tokens (int4) /  91 (int8)
    "Going along Slushy Country roads Speaking  in School Day For a
     fortnight He'll have  an appearance At some On Sunday morni and  he can
     come to  immediate"
```

Source: `I:/Temp/sotto-acc/carry_probe.py`, both arms in one process on the same
encoder cache.

One further convention was checked and found immaterial: feeding
`[blank] + last-10-symbols` (the old `pending` shape) versus feeding only the
new symbol produced **byte-identical** transcripts, so the O(1) form ships.

## 4. The four arms (CUDA vs CPU × INT4 vs INT8), all fluent

`worker/runs/p-*.jsonl` / `.err`:

|---|---|---|---|---|---|

| INT4 / CPU | CPU | 81 | 0.792 | 1892.3 | same, 81 tokens |
| **INT8 / CUDA** | CUDA, CPU | **94** | **0.144** | **2393.7** | `Going along slushy Country roads speaking damp in dr drafty school day For a fortnight He'll have an appearance At some Sunday morning and he can come to immediate` |
| INT8 / CPU | CPU | 91 | 0.483 | 2427.5 | same, 91 tokens |

Reference for the same audio, sherpa-onnx INT8 (from the predecessor audit):
`Going along slashy country roads and speaking to damp audiences in draugty
schoolrooms day after day for a fortnight, he'll have to put in an appearance at
some place of worship on Sunday morning and he can come to` — 39 words,
RTF 1.334, peak RSS 792.6 MB, CPU.

**Peak RSS next to int4's measured 2130.3 MB:** the shipped INT8 route is
**2393.2–2396.0 MB**, i.e. **+263 MB**. INT4 with the corrected walk is
**2129.1–2131.4 MB**, unchanged from before. The INT8 export buys ~14 more
tokens (94 vs 80, +17 %) for 1.07 GB of disk and 263 MB of RAM. Both are
fluent; INT4 is the cheaper arm and is not a degraded one any more.

**RTF — is the new route fast enough for real time?** Yes, with an order of
magnitude of headroom. RTF 0.144 on CUDA means 6.9× faster than real time; the
worker consumes 560 ms of audio per chunk and takes ~81 ms. On CPU it is 0.483,
which is still real-time-capable. The sherpa-onnx INT8 arm the brief pointed at
is **not**: RTF 1.334 on CPU and RTF 2.191 with `provider=cuda` (measured here,
`I:/Temp/sotto-acc/cuda_probe.py` — sherpa's CUDA provider needs
`sherpa_onnx/lib/onnxruntime_providers_cuda.dll` plus the torch/nvidia cu13 DLL
dirs on the path, and even loaded it is slower than its own CPU path at this
65-frame granularity). **That route would not have kept up; it was not taken.**

## 6. What changed in the source

| file | change |
|---|---|
| `worker/sotto_worker.py` | `run_chunk`: label cursor removed, prediction taken at the decoder's last position, `h`/`c` re-primed per chunk, one joint call per (frame, label) cell |
| `worker/sotto_worker.py` | new `_initial_encoder_caches()`: cache shapes read from the encoder graph and cross-checked against `genai_config.json`'s `left_context` (was hard-coded `(1,24,56,1024)`) |
| `worker/sotto_worker.py` | `choose_providers()`: short names (`cuda`, `cpu`, `trt`) map to the full provider names, and an explicit request is honoured exactly |
| `worker/config.json` | `model.dir` → `models/nemotron-3.5-asr-streaming-0.6b-int8` |
| `worker/README.md` | model, decode, providers and known-limitation sections rewritten to the measured facts |
| `worker/models/nemotron-3.5-asr-streaming-0.6b-int8/` | new, 1070.6 MB |

The provider-flag fix is not cosmetic: before it, `--providers cpu` was silently
overridden by an append loop and the "CPU" arms ran on CUDA, and `--providers
cuda` matched nothing and was dropped as unregistered. Both made the CPU/CUDA
comparison in §4 impossible to measure honestly.

## 9. SELF-AUDIT

**protocolos em falta.** Two, both of which cost me a wrong turn.

1. *Vary one variable.* The brief said "the int4 path is PROVEN to be what eats
   the words" and told me to replace it. I did not first ask whether the
   proposition was still true — I went looking for an INT8 export to install,
   and only discovered by accident (the INT8 export through the OLD walk
   returned word salad) that the premise was false. The protocol I lack is
   falsification-first: when a brief hands you a proven root cause, the first
   experiment should be the cheapest one that would **overturn** it, not the
   one that implements it. Here that was "run non-int4 weights through the code
   you already have" — one ten-minute run, and it would have saved the download
   and the route change.
2. *Name the instrument before trusting the number.* `--providers cpu` silently
   ran on CUDA and `--providers cuda` silently ran on CPU. I nearly published a
   CPU-vs-CUDA comparison built on a flag that did nothing. The rule I lack:
   before using a switch as a variable, prove the switch moved — by reading what
   the session reports back, not what was requested.

**verificacao adicional.** I ran three; two changed the work.

* *INT8 through the OLD walk.* Before it, "the driver is wrong" was a
  hypothesis. After it, with non-quantised weights producing the same salad, it
  is a measurement. It is the run this whole document rests on.
* *Carry-vs-re-prime, both conventions in one process over one encoder cache.*
  Without it I would have shipped a walk that looks fluent and still duplicates
  word tails — which is exactly what my first corrected version did (89 tokens,
  `country roadss`, `fortnightnight'll`). I only caught it by chasing a 6-token
  discrepancy against my own earlier probe instead of writing it off as noise.
* *Three repeat runs of the corrected selftest*: 94/94/94 tokens, identical
  text, so the quoted transcript is a property of the walk, not of one lucky
  float.

The cheap check I did **not** run: a human-transcript WER. There is no reference
for these CDN samples in the repo and the web path was not used, so every
"better" and "worse" here is against a model output.

**checkboxes novas.** For "swap a model's precision or runtime" work:

* (a) **run the new weights through the OLD driver before installing
  anything** — one command, and the only thing that separates "the new thing is
  better" from "the new thing is different";
* (b) **assert the execution provider from the session's own answer** —
  `assert asr.providers == requested` is one line and turns a silent no-op into
  a visible one;
* (c) **a doubled-tail check**, because "fluent-looking" and "correct" are
  different claims and only the second catches a mis-primed state.

**review por outro subagente.** sim-com-escopo: an independent re-run of the
four arms in §4 by someone who did not pick the walk, to test whether "INT8
recovers ~17 % more tokens" and "the carry convention causes the doubling" are
facts about the models or artefacts of how I wired the probe. I accept being put
through it. Not done here — it is a second session's work, and both probes are
reproducible from the commands in §2 and §4.

**gate-doubt:**

* **verde-de-verdade:** The `rc=0` on the old walk was the most load-bearing
  green in this repo's history: 37 tokens of word salad with a zero exit code is
  what let "the int4 quantisation" stand for two days. No existing check
  measured exit code and transcript quality together. The provider flag is the
  second: the `model-loaded` line reported `providers` all along and I read it
  only after finding my "CPU" arms were on CUDA — the field that would have
  caught my error was already in the evidence I had. The one green I trust
  completely is the carry-vs-re-prime arm: both conventions in ONE process over
  ONE encoder cache, so nothing else could differ.
* **falta-no-gate:** Nothing checks that a transcript is *words*. A future
  change to the decode loop, the feature front end, or the model directory
  passes every existing gate: `--selftest` exits 0 on word salad, and this
  README's own example JSONL was `"text":"go"`. The scenario that breaks:
  someone edits the carry convention in `run_chunk` for speed, gets RTF 0.10 and
  a green run, and ships `fortnightnight'll` to the panel.
* **gate-melhor.** A transcript check inside the selftest that fails on the
  failure I actually hit:

  ```
  python worker/sotto_worker.py --selftest --audio worker/assets/sample1.flac | \
    python -c "import sys,json,re;t=[json.loads(l) for l in sys.stdin if 'selftest-done' in l][0]['text'];\
d=re.findall(r'\b(\w)\1\b',t);print('DUP-TAIL' if d else 'OK');raise SystemExit(1 if d else 0)"
  ```

  It must be RED on this document's own before-arm output
  (`worker/runs/ACCEPT-before.err`, which contains `Coun`/`Scho`) and on the
  intermediate doubled run, and GREEN on `worker/runs/ACCEPT-after.err`. A
  second RED input: the same transcript with `tokens < 40`.
* **confianca.** **alta** for "the greedy walk was the defect, and INT4 and INT8
  are both fluent now" — a before/after on the same file and provider,
  reproduced three times, plus the decisive non-quantised-through-the-old-driver
  run. **media** for "INT8 is worth 263 MB and 1.07 GB" — one file and a token
  count, not a WER. **baixa** for anything about live conditions: one 20 s run
  of clean read speech into a virtual cable.
* **nao verificado.**
  * That the INT8 export is better on anything other than these two clean
    read-speech clips. It has `downloads=0` on the Hub and no published eval.
  * `use_vad=true` — never exercised with the new walk.
  * `lang_id != 0` — only ever 0.
  * Noise, far-field, music, overlapping speech, non-English.
  * Long-run stability: the longest continuous run is 20 s. The encoder cache
    and the per-chunk re-priming have not been watched over minutes or hours.
  * That the panel renders the new caption stream correctly — the shell was not
    launched. The JSONL is byte-compatible by inspection and by the purity
    check, not by a rendered frame.
  * Whether `blank_frac` ~0.64 in the corrected walk means anything: the
    counter's semantics changed with the walk, and its historical reference
    values (0.4800, 0.7562) were measured against the old one.

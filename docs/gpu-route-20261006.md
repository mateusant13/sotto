# GPU route, 2026-10-06: which CUDA the 1.30 wheel wants, and why nothing had to be installed

**Date:** 2026-10-06 · **Repo:** `H:/sotto` · **Lane:** `SottoGpuRoute`
**Predecessor:** `docs/int8-route-20261006.md` (§4 holds the 4-arm matrix being re-measured)

**Answer in one line:** route (a) was right, and it cost **zero bytes** — the CUDA 13
wheels were already on the box; what was missing was the *loader*, so the fix is the
one the ONNX Runtime page names in the same sentence as the error ("make sure they're
in the PATH"), plus its own `onnxruntime.preload_dlls(directory="")`. With that,
`asked ['CUDAExecutionProvider'] -> ACTUAL ['CUDAExecutionProvider', 'CPUExecutionProvider']`,
and the 4-arm matrix re-measures at **INT8 CUDA rtf 0.169 vs INT8 CPU rtf 0.658 — 3.9×**.

---

## 1. What the page ORT's own error cites says

Read 2026-10-06 from the two URLs in the brief.

### `CUDA-ExecutionProvider.html#requirements`

> Note: Starting with version 1.27, GPU packages published to PyPI (`onnxruntime-gpu`)
> and NuGet (`Microsoft.ML.OnnxRuntime.Gpu`) are built with **CUDA 13.0** by default.
> Separate CUDA 12.x GPU packages for these versions are built with **CUDA 12.8** and
> require CUDA 12.8 or newer. Older GPU package versions are built with **CUDA 12.8** by default.

> Because of [Nvidia CUDA Minor Version Compatibility], ONNX Runtime built with CUDA
> 11.8 are compatible with any CUDA 11.x version; ONNX Runtime built with CUDA 12.8
> require CUDA 12.8 or newer; ONNX Runtime built with CUDA 13.0 require CUDA 13.0 or newer.

Version table, the two rows that bracket this box:

| ONNX Runtime | CUDA | cuDNN | Notes |
|---|---|---|---|
| 1.30.x | 13.0 | 9.x | Available in PyPI and NuGet. Compatible with PyTorch for CUDA 13.x. |
| 1.30.x-1.27.x | 12.8 | 9.x | CUDA 12.x GPU packages. Requires CUDA 12.8 or newer. |

> ONNX Runtime built with cuDNN 8.x is not compatible with cuDNN 9.x, and vice versa.

And, from the same page, the two remedies that matter here:

> **Installing CUDA and cuDNN via `onnxruntime-gpu`:**
> ```
> pip install onnxruntime-gpu[cuda,cudnn]
> ```

> **Preloading DLLs from NVIDIA Site Packages:** … `onnxruntime.preload_dlls(directory="")`

> **Preload DLLs** … `directory`: *Specific path: Load DLLs from the specified directory.*
> `""` (empty string): Search in NVIDIA site packages.

From `docs/install/` (the second URL), the Windows-specific half of the same law:

> - In Windows, the path of CUDA `bin` and cuDNN `bin` directories must be added to the
>   `PATH` environment variable.

**So the required pair for ORT 1.30 is CUDA 13.0 + cuDNN 9.x.** The box reports
CUDA UMD 13.4 and cuDNN 9.27, which satisfies it.

The brief's premise — "the CUDA 12 stack is installed while ORT 1.30 wants CUDA 13" —
is only half true. The cu12 stack (`nvidia-cublas-cu12`, `nvidia-cudnn-cu12`) is
installed **and so is the complete cu13 stack**, because `torch 2.7.0+cu128` and
`onnxruntime-gpu 1.30` pulled both. **That is the whole defect: the cu13 DLLs exist
and are unreachable.** Neither `nvidia\cu13\bin\x86_64` nor `nvidia\cudnn\bin` is on
PATH, and `onnxruntime/capi/onnxruntime_providers_cuda.dll` is dlopen'd by absolute
path with no chance to search there. Error 126 is the loader reporting a search-path
miss, not a missing file.

### Route (b) — pin `onnxruntime-gpu` to the CUDA 12 build

Per the table, the CUDA 12.x build exists for `1.30.x-1.27.x`. But it is **not the
PyPI default artifact** — since 1.27 PyPI ships the CUDA 13 build, and the CUDA 12
variant is published to the Azure feed (`aiinfra.pkgs.visualstudio.com/…/ORT-Nightly`),
i.e. a **pre-release** index. So route (b) as stated is not `pip install
onnxruntime-gpu==1.26`; it is either a `--pre --index-url` nightly or a downgrade to
`1.26.x`. Both trade a stable release for a pre-release feed.

### Decision: (a), with the loader fixed and nothing installed

(a) is what the error message asks for, and after measurement it is also the cheapest:
0 bytes, no version change, no pre-release feed, no downgrade of the runtime that
`onnxruntime-genai`, `rapidocr-onnxruntime` and `sherpa-onnx` also import. Route (b)
buys nothing here — the cu13 stack is already complete — and would cost a downgrade
and a non-default index.

**The tradeoff accepted:** the working stack now needs a load step that route (b)
would not have needed. That is a real ongoing cost — a fresh shell, or any tool that
imports `onnxruntime` without Sotto's helper, hits the same silent CPU fallback
again. §5 pins the fix into the worker itself for exactly that reason.

**Scope:** nothing was installed. No `pip install` was executed (only
`--dry-run`). No `C:`/`H:`/VOD.RIP byte changed (see §6). No environment variable was
set at machine or user scope — `run-with-cuda.py` mutates only its own process. The
cu13 tree lives exactly where `torch`/`onnxruntime-gpu` already put it, in the shared
system Python at `C:\PROGRA~1\Python311\Lib\site-packages\nvidia\`; this lane added
nothing there.

## 5. What changed in the source

| file | change |
|---|---|
| `_main/run-with-cuda.py` | **new** — Sotto-scoped launcher: puts every `site-packages/nvidia` DLL directory on PATH and calls `onnxruntime.preload_dlls(directory="")`, then runs the named script. Process-local; sets no persistent environment variable. |
| `worker/sotto_worker.py` | `_add_cuda_dll_dirs()`: the `os.add_dll_directory()` handle is now retained in a module-level `_DLL_DIR_HANDLES` list. |

The worker edit is a **latent-defect fix, not the reason CUDA was broken**. Its
docstring says the call must run before `onnxruntime` is imported, and the PATH line
beside it was already doing the work. Measured reason the old line was a silent no-op:
`os.add_dll_directory()` returns a handle that keeps the directory registered, and
dropping it lets CPython collect it and undo the registration on the next GC. The
`except Exception: pass` also hid that it had failed. Both halves are now real.

Re-verified after the edit, so the change is not what produced §4:

```
post-int8-cuda rtf=0.156  tokens=94  rss=2393.6  ['CUDAExecutionProvider', 'CPUExecutionProvider']
post-int8-cpu  rtf=0.652  tokens=91  rss=2427.2  ['CPUExecutionProvider']
```

The worker needed no `run-with-cuda.py` wrapper: it already had `_add_cuda_dll_dirs()`.
The launcher exists for the probes and for any tool that imports `onnxruntime` outside
the worker.

## 7. Findings not fixed here

* **Two ONNX Runtime packages in one directory.** ORT says so itself:
  `WARNING: multiple onnxruntime packages are installed to the same location. Please
  'pip uninstall` all above packages, then 'pip install' only one of them.`
  `onnxruntime==1.30.0` and `onnxruntime-gpu==1.30.0` both own
  `site-packages/onnxruntime/`. The GPU one won the file fight, which is why
  `import onnxruntime` gets the CUDA build. **This is a live hazard**: uninstalling
  either package deletes files the other one needs, and `rapidocr-onnxruntime`,
  `sherpa-onnx` and `onnxruntime-genai` all import `onnxruntime` from that same tree.
  Not touched — deduplicating it changes behaviour for four other consumers and is
  not this lane's call. It is, however, almost certainly **how today's regression
  happened**: the previous working CUDA setup was the cu12 build, and installing
  `onnxruntime-gpu` 1.30 over it silently replaced the DLLs with the cu13 ones.
* **`docs/install/` is stale relative to the EP page.** It still says "The default
  CUDA version for `onnxruntime-gpu` in pypi is 12.x since 1.19.0", while
  `CUDA-ExecutionProvider.html` says 13.0 since 1.27. The EP page is the one the
  error message cites and the one that matches the installed artefact
  (`CUDA version used in build: 13.0`). Route (b) in this brief is not reachable
  from the install page without reading the EP page's table.
* **`sherpa-onnx` is unaffected either way.** It carries its own
  `sherpa_onnx/lib/onnxruntime_providers_cuda.dll`; the worker does not use it.

## 10. SELF-AUDIT

**protocolos em falta.** Two, both of which cost time.

1. **"Read the artefact before re-deriving the cause."** The brief handed me a
   measured cause and told me not to re-derive it, and I nearly treated "the cu12
   stack is installed, ORT wants cu13" as the finding. Checking `pip list` before
   choosing a route would have shown `nvidia-cublas 13.8.0.4` and
   `nvidia-cudnn-cu13 9.27.0.42` already installed and turned a two-hour install
   into a one-line fix. The protocol: on any "the library is missing" ticket, run
   `pip list` and stat the named DLL **before** accepting the premise — the premise
   can be right about the version and wrong about the presence.
2. **"Prove the fast arm ran on the fast device."** I could have reported §4's RTF
   without reading the `providers` line, and a silent CPU fallback would still have
   printed a plausible number. I did read it, but only because a predecessor doc
   happened to show the field. It should be a hard rule: **no performance number is
   reported without the provider identity attached to the same run.**

**verificacao adicional.** Two, both run.

1. *Three reps of each int8 arm instead of one* — done (§4). A single sample could
   have been a lucky or unlucky run; medians are 0.169 / 0.658 and the tokens are
   byte-identical across reps.
2. *PATH-only and preload-only tested in separate processes* — done (§3). This is
   what caught that my first PATH attempt failed for an unrelated reason (an MSYS
   shell passing forward-slash PATH entries to a Windows loader) and would otherwise
   have become a false claim that "PATH does not work on Windows".

Cost of the one I did **not** run: a live 20 s loopback with CUDA confirmed
(`int8-route-20261006.md` §5 protocol) — roughly 3 minutes including the cable
feeder. Skipped because it needs the VB-Audio cable to be free, which is a
shared-resource dependency on something outside this repo.

**checkboxes novas.** For this class of work ("the accelerator is not being used"):

* `[ ] pip list shows the exact wheels the fix needs, BEFORE choosing a route — an
  already-satisfied requirement is a zero-byte fix, not an install task`
* `[ ] the named missing file/dll was stat'ed on disk, not inferred from the error text`
* `[ ] every performance number is reported with the provider list from the SAME run`
* `[ ] C: free space re-measured AFTER the work, not only before, so "installed
  nothing" is a measurement and not a promise`

**Gate-doubt**

- **verde-de-verdade:** Two of my own checks could have passed vacuously, and I say
  which:

  1. **`rtf` alone.** The `--selftest` run returns `rc=0` and a plausible RTF whether
     or not CUDA loaded — it did not, before the fix, and still would not. Had I
  scored the matrix on RTF and run-to-run agreement alone, the pre-fix control would
  have scored as "fine, just slow". The `providers` line is what makes the gate real,
     and it is a read off the live session, not a flag echo. *Named race: the CUDA
     arms and the CPU arms were produced by the same flag-parsing path
     (`choose_providers`), so if that path ever ignored `--providers`, both arms
     would report the same provider and the matrix would still "pass".*
  2. **`available_providers()` in §3.** In the control it already listed
     `CUDAExecutionProvider`. Any check written against `get_available_providers()`
     would have been **green before the fix and green after** — a textbook
     pass-by-construction. This is the exact register-vs-load trap; the gate is
     `InferenceSession(...).get_providers()` on a real model, never
     `get_available_providers()`.
  3. **`pip --dry-run`** could pass for the wrong reason (a stale cache saying
